# DDS v2 三类输入与操盘优化升级策略

- 状态：产品方向已确认，待分阶段实现
- 日期：2026-07-23
- 适用版本：DDS v2 当前 `SC-AD-VA-CS`、EvidencePackage 与 V4 ReportDocument 链
- 替代范围：替代 `DDS_v2数据驱动升级计划.md` 中“固定一种报告深度”和“用通用基准补齐缺失数字”的产品方向；不推翻已经完成的真实性、冻结、编译和交付门禁

## 1. 战略结论

DDS v2 下一阶段不再只是“把一份报告补完整”，而要升级为面向不同资料成熟度的地产前策与操盘决策系统：

1. 根据输入成熟度进入三种报告模式，而不是要求所有项目一开始就满足同一深度。
2. 使用“整体 Input 模式 + 模块级证据门禁”，避免用一张强排图推断所有市场、成本和去化结论。
3. 同时生成多种产品定位、设计、营销和推售策略，并在统一口径下模拟。
4. 不以最快去化或最高静态货值作为单一答案；寻找去化、货值、回款、投入和风险之间的 Pareto 最优路线。
5. 大模型负责提出和解释策略，确定性引擎负责分类、计算、比较、冻结和门禁。

目标函数不是“卖得最快”，而是：

```text
风险调整操盘价值
= 回款现值
− 产品与展示增量成本
− 营销投入
− 库存资金占用
− 尾盘折价与市场波动风险
```

## 2. 三类 Input 与报告产品

### 2.1 Input 1：场地机会研判

最低输入：

- 可解析的坐标或地址。
- 用户对项目的粗略描述。
- 希望回答的决策问题。

报告回答：“这个位置可能适合做什么，下一步值得验证什么？”

允许输出：

- 区位、板块、市场和竞品扫描。
- 客群及需求假设。
- 多种产品定位和概念设计方向。
- 每种定位对应的营销、展示和推售策略。
- 以 100 套为标准盘的去化压力测试。
- 相对价格指数、静态货值指数、实现货值指数和回款现值指数。
- 保守、基准、积极三种市场情景。
- 升级到 Input 2 的补证清单。

禁止输出：

- 无来源的真实面积、套数、绝对售价、总货值和成本。
- 法定合规结论。
- 项目确定售罄周期、IRR、ROI 或确定性溢价。

Input 1 可以对 `opportunity_screening` 决策范围正式就绪，但不得升级为拿地、定价或投资决策就绪。

### 2.2 Input 2：约束驱动前策

进入条件：在 Input 1 基础上，已经提供一项或多项具有明确限制条件和标准的材料，例如控规、详规、规划条件、用地条件、任务书、产品标准或成本边界。材料可以不齐全，但必须保留来源、版本和日期。

报告回答：“在当前明确约束下，大致可以怎么做，哪条操盘路线最有价值？”

新增输出：

- 条件登记表以及已确认、待核实、冲突、过期四类状态。
- 容量、业态、户配、分期和开发节奏区间。
- 约束驱动的概念方案模拟。
- 真实项目货量模拟；只有面积和套数有合格来源时才从标准 100 套切换。
- 初步静态货值、实现货值和现金流压力测试。
- 设计动作、客户体验、营销卖点和去化影响之间的因果链。
- 缺失条件对方案和测算的敏感性。

禁止输出：

- 自动补齐缺失控规或把非权威资料写成法定事实。
- 资料不足时宣告正式合规。
- 缺少价格、成本或节奏依据时输出确定投资结论。

### 2.3 Input 3：方案决策比选

进入条件：Input 2 的核心开发边界基本可用，并且存在可审计的方案、概念强排、户配或结构化方案数据。至少应有两个可比较方案；可以是多个甲方方案，也可以是“现有方案 + DDS 生成的替代方向”。

报告回答：“哪种方案及其操盘组合更优，为什么，何时切换？”

新增输出：

- 多方案口径归一与输入勾稽。
- 规划效率、产品结构、设计体验、市场匹配、成本和实施难度比较。
- 每个方案对应的定价、供货、营销和去化策略。
- 静态货值、预计实现货值、回款现值、资金峰值和尾盘风险。
- 多目标 Pareto 前沿、推荐路线和淘汰理由。
- 首开、加推、调价、渠道和产品切换触发器。
- 真实销售数据回填后的滚动校准。

Input 3 仍不自动等于 VA1/VA2 可评估。方案资料不能替代市场需求、成本、价格和结果变量证据。

### 2.4 可执行报告模式矩阵

内部继续保留单一十二单元状态，客户页面只渲染当前 mode 的必显单元和有实质内容的条件单元；`unknown` 进入门禁、补证和审计记录，不生成客户可见的空占位页。

| 模式 | 决策问题 | 必显内容 | 条件内容 | 禁止结论 | 升级／降级触发 |
| --- | --- | --- | --- | --- | --- |
| Input 1 | 是否值得继续研究，可能采取什么定位 | SC1、SC2、策略 AD1/AD2、概念 AD3/AD4、标准盘 VA2、VA3、CS | 场地公开信息、文化解释、定性 VA1 | 绝对面积、人民币货值、确定售罄、合规和投资结论 | 获得明确约束材料可升 Input 2；位置不可解析则阻断 |
| Input 2 | 在现有约束下哪条前策路线更优 | SC1–SC3、AD1–AD4、情景 VA2、VA3、CS | AD5、具备成本价值证据的 VA1、实际货量 | 缺资料时的正式合规、确定收益和伪精确强排 | 核心边界与方案可审计时升 Input 3；约束冲突或过期时字段级降级 |
| Input 3 | 多个方案与操盘组合中如何选择 | SC1–SC3、AD1–AD4、VA1–VA3、CS 与方案前沿 | AD5、滚动销售校准 | 把方案图当需求／成本证据、全方案失效时强行推荐 | 方案或经济输入失效时退回 Input 2；真实销售反馈触发滚动校准 |

Input 2 的进入条件只提高可处理的报告模式，不提高所有字段的 quantitative authority。例如一份成本标准只能提升对应成本字段，不能同时把法定条件、客户需求或售价标为已验证。

## 3. 输入模式不能替代模块证据门禁

项目先形成 `InputProfile`，至少评估七个维度：

| 维度 | 典型内容 |
| --- | --- |
| 项目身份与位置 | 坐标、地址、城市、地块身份、基准日 |
| 法定与规划条件 | 红线、用地、容积率、限高、退界、日照、配建 |
| 开发任务与目标 | 项目类型、回款目标、品牌目标、开发节奏、风险偏好 |
| 市场与客户证据 | 竞品、成交、供求、总价带、客户池、渠道与转化 |
| 产品与方案 | 户配、面积、套数、总图、强排、方案版本 |
| 成本与资金 | 地价、建安、增量成本、税费、融资、营销预算 |
| 销售与运营反馈 | 来访、认购、签约、退房、折扣、库存、回款 |

每个维度和字段保持现有真实性语义：`verified / estimated / simulated / unknown / conflict / stale`。Input 模式只决定报告要回答的问题和最大深度，不会把弱证据自动升级。

需要新增三个相互独立的状态：

- `analysis_profile`：包含 `requested_level / assessed_level / effective_level`，界面显示为 Input 1/2/3；代码不使用裸 `mode`，避免与现有 ProductMode 和阅读／演示 mode 冲突。
- `decision_scope`：本报告允许支持的决策，例如机会筛选、约束前策或方案选择。
- `module_readiness`：SC、AD、VA 各模块自己的事实和计算就绪度。

`delivery_ready` 必须绑定 `decision_scope`。Input 1 可以是可交付的机会研判，但其拿地、定价和投资门禁仍保持关闭。

`analysis_profile` 应同时决定三件事：unit policy、Requirement Graph 和 quantitative authority。三者必须由同一个 profile registry 生成，供 RequirementAgent、ContractEnforcer、ReportService、ReportCompilerAdapter 和 ReportDocument 共用；不得在领域契约、研究 Agent 和报告层各维护一份容易漂移的模式矩阵。

unit policy 使用 `required / optional / excluded` 三态，并派生：

- `required_units`：参与交付门禁。
- `included_units`：required 加上具有合格内容的 optional，参与客户页面渲染。
- `excluded`：只留内部审计，不进入客户页面。AD5 默认 opt-in/optional，不作为所有模式的统一硬门。

## 4. 操盘策略沙盘

### 4.1 两个正交维度

必须分开处理：

- 操盘策略是开发团队可以主动选择的变量。
- 市场情景是外部环境及不确定性的变量。

默认生成三套有实质差异的操盘组合，每套分别运行保守、基准、积极市场情景，共形成九条主要去化曲线。为防止报告膨胀，只展示非支配方案、推荐方案和关键反例，其余结果进入附录。

默认策略原型可以包括：

| 路线 | 价值逻辑 | 典型动作 | 主要风险 |
| --- | --- | --- | --- |
| 快周转 | 牺牲部分价格空间换取流量和现金回收 | 控总价、集中首开、渠道蓄客、快速供货 | 同质化、价格锚定过低 |
| 均衡改善 | 在产品力、价格和流速之间寻求稳健平衡 | 户型分层、适度溢价、分批推售、内容与渠道并行 | 对执行一致性要求较高 |
| 标杆溢价 | 用稀缺体验和品牌表达争取更高价值 | 强展示、强场景、控制供货、逐级释放价值货源 | 蓄客长、投入高、尾盘风险大 |

这些只是策略原型。系统应依据场地与市场生成低密、文旅、青年、康养、产业配套等更适配的路线。

### 4.2 最优路线通常是组合而非单一定位

系统必须允许一个推荐路线由多个产品角色组成：

- 流量产品：降低首开门槛，形成成交和回款。
- 主力产品：承担主要货量和稳定去化。
- 价值产品：利用楼层、景观、稀缺资源实现价格抬升。
- 推售顺序：先形成市场证明，再释放高价值货源。
- 动态策略：根据来访、认购、签约和库存结构触发调价、加推或降级。

推荐结论应表达为“产品组合 + 价格阶梯 + 供货顺序 + 营销动作 + 切换触发器”，而不是只选 A/B/C 标签。

营销策略必须结构化进入模拟，而不是只保留叙事。每个 StrategyCandidate 至少登记渠道组合、预计获客量与成本、来访→认购→签约转化、蓄客期、展示投入、首开／加推／调价规则及证据状态。没有证据时只能以区间或强度等级进入情景，不能进入人民币收益优化。

## 5. 去化与货值联合计算

### 5.1 Input 1：标准盘与指数

Input 1 使用 100 套标准盘，避免伪造项目真实规模。允许输出：

- 月度去化率和剩余库存曲线。
- 3/6/12 个月累计去化率。
- 标准盘清盘周期区间。
- 相对竞品的价格指数。
- 静态货值指数、实现货值指数和回款现值指数。
- 尾盘占比、折价压力和营销投入强度等级。

所有数字必须标记为 `model_simulation`，并冻结参数版本、种子、证据引用和假设。没有合格的城市或板块参数时，返回不可模拟，不允许使用全国通用默认值。

### 5.2 Input 2/3：真实项目量纲

只有以下输入具备来源和版本后，才能输出人民币货值或项目现金流：

- 可售面积、套数、面积段和供货批次。
- 售价或价格情景及其依据。
- 地价、建安、增量设计、展示、营销、税费和融资条件。
- 认购、签约、回款和退房口径。

不能把标准 100 套结果按总套数线性放大。真实货量会改变客户池消耗、批次竞争、渠道容量、季节性和尾盘结构，必须重新运行模型。

### 5.3 多目标比较

每个策略至少比较：

- 12 个月去化率和清盘周期。
- 静态货值与预计实现货值。
- 回款净现值和资金峰值。
- 产品、展示和营销增量投入。
- 尾盘库存、折价和市场转弱损失。
- 对关键参数变化的敏感性。

系统先输出 Pareto 最优策略集，再根据开发目标排序。用户未指定风险偏好时，只输出条件式推荐，不硬编码唯一最优；明确风险偏好后，以风险调整后的回款现值作为主排序，同时展示最快去化和最高实现货值两个对照方案，不能隐藏目标权重造成的取舍。

实现前必须冻结财务口径，区分静态货值、预计实现货值、回款现值、回款净现值和风险调整操盘价值。成本、税费、融资和风险惩罚只能在定义的层级扣除一次，避免重复扣减。

风险调整指标建议采用可审计形式：

```text
RiskAdjustedNPV = E(NPV) − λ × CVaRα(下行损失)
```

其中 `λ` 和 `α` 是项目或开发商确认并冻结的风险偏好，不是系统隐藏常量。

### 5.4 目标计算契约

正式实现前先冻结以下最小契约：

- `StrategyCandidate`：定位、客群、产品组合、价格阶梯、供货、营销、设计投入和触发器。
- `MarketScenario`：需求、价格弹性、竞品、季节性、渠道容量和场景概率。
- `SimulationAssumptions`：参数值、区间、来源、时间窗、版本和随机种子。
- `MonthlyResult`：月初库存、新增供货、认购、签约、退订、成交货值、现金回款、支出和月末库存。
- `StrategyOutcome`：去化、实现货值、回款现值、峰值资金、尾盘和风险指标。
- `ParetoDecision`：硬约束、目标向量、非支配集合、推荐条件、淘汰理由和切换触发器。

唯一计算主链为：

```text
月度去化 → 实现货值 → 现金回款 → 风险调整 NPV
→ Pareto 非支配策略 → 动态操盘触发器
```

## 6. 大模型与确定性引擎边界

### 大模型负责

- 根据场地、市场和约束提出差异化定位与操盘路线。
- 形成设计思路、客户价值主张和营销叙事。
- 提出策略因果链、反证、风险和切换动作。
- 解释模拟结果和路线之间的取舍。

### 确定性模块负责

- InputProfile 分类和报告模式上限。
- 数据资格、来源、版本、冲突和时效判断。
- 户配、面积、货值和现金流勾稽。
- 去化、折扣、回款、库存和敏感性计算。
- Pareto 支配判断和排序。
- EvidencePackage 冻结、ReportDocument 编译和交付门禁。

Writer 和大模型不得新增计算结果之外的客户可见数字。

## 7. 当前能力与新增能力

### 可直接复用

- `ProjectContext`、EvidenceType、六种证据解析状态和模块级门禁。
- `ProductEngine` 的概念方向与已有方案审计双模式。
- `ABMEngine` 的城市参数版本、固定种子、客群选择和 WTP 模拟。
- `PremiumEngine` 的 fail-closed 基准、成本和证据检查。
- `SC-AD-VA-CS` 十二单元、EvidencePackage、V4 ReportDocument 和 hash-bound QA。
- ResearchJobService、主动研究源、候选证据资格判断和运行日志。

### 实际缺口

- 当前没有 Input 1/2/3 的确定性分类器及决策范围语义。
- RequirementAgent 当前固定生成 SC2 → AD1 → AD2 → AD3 → AD4 → VA1，尚未按输入模式覆盖 SC3、VA2、VA3 和 CS。
- ContractEnforcer 当前按全部十二单元执行结构、证据、决策和置信度门；若只在报告层裁剪，会形成“页面可编译、上游永远不 ready”的双重口径。
- ABM 目前输出选择份额和 WTP，不是月度去化、库存和回款模型。
- VA1 目前主要覆盖售价溢价场景，尚未形成去化与货值联合优化。
- VA2 在报告契约中已有位置，但缺少生产级销售、现金流和风险调整价值引擎。
- ProductEngine 只有概念方向或单方案勾稽，没有跨方案的统一经济比较与 Pareto 筛选。
- 当前产品 API 以研究任务为中心，尚无输入画像、策略沙盘、方案比较和决策范围接口。
- 当前 ReportDocument 已预留 `absorption_forecast` 和 `investment_case`，但 ReportCompilerAdapter 尚未把 VA2 形成一等策略比较页面。
- 当前 listing repository 虽读取原始去化字段，但没有形成 30/90/180 天供应、价格、库存、促销和签约时序；挂牌截面不能直接校准月度去化。
- 当前 ReportService 和 Requirement Graph 的业务主链停在 VA1，尚未主动采集、解析或装配 VA2 的销售、回款、融资和税费输入。
- ReportService 当前不会把完整 requirements、输入画像、模型版本和策略目标保存进正式 ReportRun，模式判级理由可能在冻结前丢失。

## 8. 分阶段升级路线

### M7：输入画像与三类报告门禁

交付：

- 定义 `InputProfile`、`AnalysisProfile` 和 `DecisionScope`；记录 requested、assessed 和 effective level。
- 按资料内容而非文件数量判断 Input 1/2/3。
- 建立唯一 profile registry，由它生成 `required / optional / excluded` unit policy、Requirement Graph 和 quantitative authority。
- 改造 RequirementAgent，不再固定生成 SC2 → AD1 → AD2 → AD3 → AD4 → VA1。
- 将同一 profile/required_units 下沉到 ContractEnforcer，四级门和置信度只评估 required units；ReportDocument 渲染 included units。
- 改造 ReportService.assemble，保存 requirements、analysis_profile、判级依据、模型版本和策略目标，使冻结包能够审计为何使用标准 100 套以及为何允许／禁止绝对金额。
- 报告首页明确输入等级、决策范围、可用结论和禁止用途。
- 保留单一 V4 ReportDocument 链，不增加平行模板系统。

验收：

- 三组固定 fixture 能稳定分类到 Input 1/2/3。
- fixture 同时覆盖字段优先级、来源冲突、过期材料和人工覆盖规则。
- 同一输入重复分类结果和哈希一致。
- requested level 不得高于 assessed level 生效；`analysis_profile`、`decision_scope` 和 `module_readiness` 不得互相自动提升。
- RequirementAgent、ContractEnforcer、ReportService、ReportCompilerAdapter 和 ReportDocument 对 required/included units 的结果完全一致。
- Input 1 能对机会筛选 `delivery_ready=True`，但投资、定价和法定结论门禁为关闭。
- 缺地址或坐标时仍 fail-closed。

### M8：Input 1 操盘策略实验室

交付：

- 生成至少三套差异化策略组合。
- 每套运行三种市场情景。
- 新增标准 100 套月度去化、价格指数、货值指数和回款现值指数。
- 输出非支配策略、推荐理由、反证和切换触发器。
- 把 DCBBS 和建筑案例作为 `restricted/internal-research` 的策略启发源；未经公开来源匹配或授权，不进入客户事实链。

验收：

- 九条模拟可复算，固定输入、参数版本和种子时结果一致。
- ABM 的 choice share/WTP 只能作为有版本的需求参数，不能直接换算清盘月数。
- 月销量不得超过当月可售库存；累计去化单调且不超过 100；期末库存勾稽；销量、库存和回款不得为负。
- 当需求参数按同方向有序变化时，结果必须保持可解释的单调关系，反例必须显式登记。
- 所有指数明确以 100 为基准并冻结公式、基准样本和时间窗。
- 任何绝对面积、总货值或人民币现金流都必须来自用户输入或合格证据。
- 没有城市参数时明确不可模拟，不使用通用城市或全国伪基准。
- 至少存在一项测试证明最快去化方案不必然是推荐方案。

### M9：Input 2 约束、真实货量与现金流模型

交付：

- 从控规、详规、规划条件和任务书形成可审计约束登记表。
- 识别版本、冲突、过期和缺失条件。
- 将容量、户配、分期和真实货量接入去化模型。
- 建立成交货值、回款时滞、地价、建安、税费、营销、融资提款与还本付息的月度现金流。
- 建立设计动作、增量成本、体验机制和销售结果之间的可撤回假设链。

验收：

- 冲突条件不得静默择一。
- 缺少法定条件时方案保持概念或条件性状态。
- 面积、套数和货值勾稽误差通过既定阈值。
- 真实项目结果不能由标准 100 套线性放大产生。
- 分批次、分户型、客户池衰减、渠道容量、季节性和尾盘效应必须进入真实货量模型。
- 认购、签约、退房、回款和期末库存按月勾稽。
- 成交货值、现金到账和会计收入分开；VA1 增量成本与溢价只能接入一次。

### M10：Input 3 多方案 Pareto 比选

交付：

- 归一化甲方方案和 DDS 替代方案。
- 同口径比较规划、产品、成本、去化、实现货值和回款现值。
- 输出 Pareto 前沿、主推组合、淘汰理由和切换条件。
- 支持“流量产品 + 主力产品 + 价值产品”的混合推售路线。

验收：

- 至少两个方案才能宣告“比选完成”。
- 冻结目标向量及方向，例如 12 月去化率↑、实现货值↑、回款现值↑、峰值资金↓、尾盘风险↓。
- 冻结硬约束、缺值处理、Pareto 支配算法和稳定排序规则。
- 被其他方案在所有目标上支配的方案不得成为默认推荐。
- 所有方案未通过硬约束时必须返回“无推荐”，不得选择相对最不差方案冒充可行方案。
- 目标权重、约束和推荐变化可追溯。
- 完成真实 Input 3 fixture 的冻结、双编译、三视口和打印 QA。

### M11：滚动校准与生产观测

交付：

- 接入来访、认购、签约、退房、折扣、库存和回款的滚动数据。
- 记录预测版本、实际偏差、参数调整和责任人。
- 建立运行成功率、来源资格率、模拟耗时、证据覆盖、模型漂移和门禁原因指标。
- 输出触发式操作建议，而不是一次性静态结论。

验收：

- 历史预测不可覆盖，只能产生新版本。
- 每次参数调整具有证据、原因和回测结果。
- 使用按时间切分的历史销售回测，预先冻结误差指标和门槛，并与朴素基线比较。
- 每个触发器必须包含信号、阈值、动作、责任人及恢复／回退规则。
- 生产观测能区分研究失败、证据不合格、模型不可运行和交付门禁失败。

### M12：真实项目回放与盲测

交付：

- 至少一个资料完整的历史项目回放，用于校准去化、回款和触发器。
- 至少一个当前项目盲测，用于验证报告对真实决策的增量价值。
- Input 1/2/3 各一套 golden fixture 和端到端交付产物。

验收：

- 回放数据严格按时间切分，模型不能读取预测时点之后的信息。
- 只有通过校准、硬约束、来源／公式覆盖和人审的项目，才能宣告“操盘优化可用于决策”。
- 三类报告均完成冻结、双编译哈希一致、三视口、打印和离线依赖 QA。

## 9. 支撑数据路线

增量同步和知识库接入不再作为独立搬库项目，而作为 M8–M11 的支撑能力：

1. curated 数据按源哈希和 schema 版本执行幂等增量同步。
2. 同步采用 staging、全量校验、原子切换和可回滚 manifest。
3. DCBBS 与建筑案例默认仅供内部研究和策略启发。
4. 客户可见结论必须使用有授权、可追溯、符合适用范围的 EvidenceRecord。
5. 每个模拟参数记录来源、城市、时间窗、样本范围和版本。

## 10. 版本冻结策略

“版本冻结”分为三层，避免把代码冻结和项目事实冻结混为一谈：

- 工程基线：源码 revision、依赖锁、测试结果和构建产物。
- 模型基线：InputProfile schema、策略生成规则、模拟公式、城市参数版本和随机种子。
- 项目基线：用户材料、EvidencePackage、输入画像、候选策略、选定目标权重和人工签署。

任何一层变化都产生新版本，不覆盖旧结果。正式报告继续执行 EvidencePackage → ReportDocument → HTML → hash-bound browser/print QA 的单一交付链。

## 11. 失败与降级策略

- 证据不足：降低字段或 `decision_scope`，不补假数。
- 参数失效：冻结旧结果，以新版本重算，不覆盖历史预测。
- Pareto 结果对情景不稳定：返回条件式推荐并显示切换区间。
- 所有方案未过硬约束：返回“无推荐”和下一步补证／改案动作。
- 外部模型或研究源不可用：登记来源失败与缺口，不静默切换全国默认值。
- 报告模式与模块就绪度冲突：以更低的 quantitative authority 为准。

每个 Input fixture 最终都必须走 EvidencePackage → ReportDocument → HTML → 三视口／打印 hash-bound QA。数字来源和公式覆盖率必须为 100%；Input 1 必须通过自动检查，确保没有人民币总货值、项目确定售罄或投资承诺。

## 12. 明确废止的旧方向

- 废止“所有字段永远有数值”的要求。结构可以完整，事实和数值可以为未知。
- 废止用城市、同类或全国通用值自动冒充项目事实。
- 废止仅按资料多少判断报告质量；改为按资料类型、证据资格和决策范围判断。
- 废止把最快去化、最高标价或最高静态货值单独定义为最优。
- 废止为三类 Input 建立三条互不兼容的报告技术链。
- 废止由大模型直接编写客户可见预测数字。

## 13. 推荐实施顺序

1. 先实现 M7，冻结三类 Input、决策范围和模式化门禁。
2. 再实现 M8，以 Input 1 的标准 100 套操盘沙盘验证核心产品价值。
3. 以真实控规/任务书 fixture 推进 M9。
4. 以两个以上真实方案推进 M10。
5. 在已有真实销售反馈后推进 M11，不提前构造伪生产指标。

武汉 VA1 不再是整个 DDS 产品升级的唯一入口。它保留为 Input 2/3 的真实补证与校准案例；在证据未补齐前继续 `not_assessable`。Input 1 则可以在严格限定的机会筛选范围内形成独立、可交付的前策产品。
